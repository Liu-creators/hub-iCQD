1. 功能架构总览
建议按四层能力栈组织功能模块，每一层解决独立问题，避免功能之间互相“兜底”：

L1 数据与语义层：数据源接入管理、语义模型（表/字段/指标/关系）、指标字典与同义词、业务术语知识库。这是 ChatBI 准确率的地基——基于语义层的 NL 查询准确率可达 83%，而直接基于原始 Schema 仅约 40%。

L2 意图理解与生成层：意图解析、Schema Linking、SQL 生成、多轮对话状态管理、澄清追问。核心功能不是“一步生成 SQL”，而是“在生成之前把问题理解到位”。

L3 可信执行与洞察层：SQL 安全校验与执行、结果格式化、自动图表推荐、轻量归因说明、异常提示。执行层是权限拦截和熔断限流的最后一道闸门。

L4 运营与反馈闭环层：会话历史与回放、查询日志、用户反馈（“数不对”/“口径不对”）、准确率监控、Bad Case 归集与回归测试集维护。

2. 核心功能模块详述
2.1 对话式问数
支持单轮与多轮递进式分析。多轮场景下，对话状态跟踪（DST）需要维护时间范围、维度、过滤条件、已引用的指标和实体，使“那华东呢？”“换成上个月”这类追问能够正确消解。前端应展示 Agent 的中间过程（意图、选表、SQL 摘要），而不是只给最终数字——可解释性是信任的前提。

2.2 Schema Linking 与澄清
用户问题往往在表名/字段名层面是模糊的。功能上需要做到：基于向量检索召回候选表，再通过双向检索（先找表再挑列、先找列再定表）合并结果，减少误召回和漏召回。当候选置信度低于阈值时，系统应主动发起澄清追问（“您指的是‘销售额’还是‘回款额’？”），而不是猜测后直接生成 SQL。

2.3 结果呈现与轻量洞察
结果不能停留在表格。功能应包括：自动图表类型推荐、关键数值标注、同比/环比等基础对比、以及“一句话解读”（例如“华东销售额环比下降 12%，主要受江苏拖累”）。解读必须基于查询结果计算，而非由 LLM 自由生成，避免产生无法对账的结论。

2.4 会话管理与审计
会话落库可追溯，支持按用户、时间、数据源、查询状态检索。每次查询需记录：原始问题、解析后的意图、选中的 Schema、生成的 SQL、执行结果摘要、耗时、权限校验结果。这是运营闭环和合规审计的共同基础。
