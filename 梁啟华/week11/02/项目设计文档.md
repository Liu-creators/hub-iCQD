1. 项目定位与边界
ChatBI 的本质不是“给 BI 加一个对话框”，而是把数据分析的交互入口从“拖拽 + 配置”切换为“自然语言 + 可解释的 Agent 过程”。它的核心价值主张有三条：

降低查询门槛：业务人员无需掌握 SQL 或 BI 工具操作即可获取数据；

缩短需求链路：从“提需求—排期—开发—交付”压缩为“提问—校验—结果”；

保留治理能力：自然语言交互不能绕过既有的数据权限、口径规范和审计要求。

项目边界需要在启动阶段明确写入文档：ChatBI 适合独立的智能问数入口，围绕会话持续生成图表和轻量看板；复杂跨域归因、深度报告编排、指标平台建设等，应由 Data Agent 或既有指标平台承接，不在首期 ChatBI 范围内。把“已交付”和“下一版规划”分开书写，是避免项目叙事失控的第一条纪律。

2. 版本分层与交付节奏
建议采用 V1 / V2 / V3 三层交付，每层有明确的“能力边界”和“验收口径”：

V1（最小可用）：规则路由 + 固定分支，跑通 RAG、Text2SQL 和流式输出，验证“自然语言问数”在目标场景中的基本可行性。V1 的合理预期是“能用”，而不是“好用”——它在复杂问题面前会暴露出决策不可解释、多步协作弱、失败只能报错的问题。

V2（Agent 化与可验收）：由 LLM 参与意图识别与工具选择，规则路由退居超时/低置信时的降级路径；引入类 ReAct 循环支持多步推理、工具切换与按失败类型回退；多轮记忆与会话落库可追溯；过程事件契约化，使前端可展示“步骤开始 / 思考摘要 / 意图结果 / 步骤结束 / 最终汇总”，而不是只看到最终答案。

V3（企业级生产化）：多租户隔离、语法级 SQL 防护、熔断限流、细粒度权限穿透、全链路审计、SLA 保障。这些能力不应提前算进 V2 的“已交付”清单，否则项目验收会陷入“功能看起来都有、生产一用就出事”的困境。

3. 关键里程碑与风险
里程碑建议按“可演示 → 可试用 → 可推广”三段设置，每段附带可量化的退出标准（例如：V2 退出标准包括在 golden set 上执行准确率不低于阈值、过程事件契约通过前后端联调、失败回退路径覆盖 Top-5 失败类型）。核心风险及应对：

风险	应对
语义口径不统一导致“数不对”	语义层先行，指标字典与同义词在 V1 前完成最小集定义
Schema 膨胀导致模型幻觉	Schema Linking 检索替代全量 Schema 注入
权限事故（服务账号越权）	权限校验靠近执行层，查询继承提问者身份而非系统服务账号
项目范围蔓延至 Data Agent 领域	项目设计文档中显式划定边界，变更走范围评审
