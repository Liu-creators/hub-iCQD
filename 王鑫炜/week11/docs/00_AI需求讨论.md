# ChatBI 项目需求讨论

本次作业选择 Chinook 音乐商店作为 ChatBI 场景，围绕“从自然语言问题得到可核对的数据答案”整理 AI 设计问答。以下追问和回答是本次 AI 辅助设计的整理，用来说明方案取舍；不是用户逐条回复的聊天原文，也未冒称在其他 AI 平台开展过额外会话。

## 项目能力讨论

**设计追问：用户到底需要什么，而不只是把自然语言翻译成 SQL？**

用户需要理解销售表现，能说清指标、时间、分组，并看到可以核对的结果。因此系统还需要识别歧义、解析表结构、解释统计口径、限制查询权限和记录执行过程。生成 SQL 只是其中一步。

**设计追问：“最近销售怎么样”可以直接生成查询吗？**

不可以。最近的时间范围和销售指标都不明确，而且课程库只有 2009—2013 年的发票。系统应追问要分析哪段时间，以及销售额还是售出数量。用户明确问 2026 年时可以查询并报告无匹配记录，不把没有记录解释成销售额为零。

**设计追问：音乐流派的销售额要用曲目目录价还是成交价？**

应使用发票明细的 `UnitPrice * Quantity`。曲目表是目录，不说明实际售出多少。如果只看 `tracks.UnitPrice`，无法算出实际销售额。发票头和明细一对多，连接后直接求和发票头 `Total` 还会造成重复计数。

**设计追问：为什么 SQL 校验后还需要失败处理？**

编译能发现语法、表和字段错误，但不能保证表达式在运行时不会溢出，也不能证明业务口径正确。执行时继续施加只读权限和预算，运行错误带着上下文回到改写阶段；达到次数上限停止。权限错误直接停止，避免让模型尝试规避。

**设计追问：是否必须使用 MCP 或 OpenAI Agents SDK？**

这次作业要求完整工作流，没有指定框架。用显式 Python 状态流可以直观看到每个阶段、入参和错误处理。MCP 是未来将元数据、查询能力开放给其他客户端的一种接口选择，不负责判定业务口径，也不会替代数据库权限。

**设计追问：没有模型 API Key 时，如何验证作业？**

使用明确标记的固定模型响应，配合真实数据库运行工作流，验证表选择、SQL 错误、修正反馈和执行结果。另在 HTTP 传输边界注入测试响应，验证真实客户端的请求和解析。两种测试都不证明真实模型效果，在线验收另用同一批业务问题执行。

**设计追问：第一版和完整产品的范围如何划分？**

第一版交付单次问题、SQLite、七步工作流、结构化执行记录、权限限制和测试。完整产品再加入 Web 查询台、受控多轮上下文、图表、身份认证、行级权限、更多数据库和监控。这样每项能力都有可验收的边界。

## 形成的交付

项目设计明确用户、目标、范围和验收指标；功能设计细化正常、澄清、改写、拒绝、部分成功等流程；技术设计给出模块、数据结构、权限和测试方法。对应三份文档与当前代码使用相同的状态名和统计口径。
