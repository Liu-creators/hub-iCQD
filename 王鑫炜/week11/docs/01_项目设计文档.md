# Chinook 音乐商店 ChatBI 项目设计

Chinook ChatBI 帮助音乐商店经营分析人员用自然语言查询历史销售、客户分布和曲目表现，并通过 SQL 和原始结果核对答案。首版采用课程 SQLite 数据库，以可追溯的查询工作流作为产品基础。

作者：王鑫炜。版本：1.0。日期：2026-10-22。

## 背景与目标

销售、曲目、专辑和艺术家分散在不同表中，回答“哪类音乐实际卖得最多”需要理解外键、明细粒度和聚合。手工查询依赖 SQL 能力；直接让模型回答又容易编造数据或混淆统计口径。

项目把问题理解和 SQL 生成交给模型，将权限、校验、执行和次数上限交给程序。每次回答展示执行 SQL、原始结果和统计解释，使分析人员能够复核。

## 用户与场景

| 用户 | 任务 | 示例 |
| --- | --- | --- |
| 经营分析人员 | 查看历史销售与国家分布 | 按账单国家列出销售额前五名 |
| 内容运营人员 | 比较音乐流派或艺术家表现 | 按流派统计销量和实际销售额 |
| 开发及数据人员 | 核对 SQL、连接、结果与失败原因 | 检查多表连接是否重复计数 |

角色用于描述需求。当前原型没有登录或不同用户身份，也不提供生产级租户隔离。

## 数据与指标

| 指标 | 定义 | 边界 |
| --- | --- | --- |
| 发票销售额 | `SUM(invoices.Total)` | 在发票头粒度求和，不能连接明细后重复累加 |
| 明细销售额 | `SUM(invoice_items.UnitPrice * Quantity)` | 适合按流派、曲目和艺术家分析 |
| 售出数量 | `SUM(invoice_items.Quantity)` | 不用明细行数或曲目目录行数代替 |
| 国家销售额 | 按 `invoices.BillingCountry` 分组 | 客户所在国家是另一口径 |
| 有专辑艺术家数 | `COUNT(DISTINCT albums.ArtistId)` | 不等于艺术家表总行数 |

课程库共有 11 张业务表，412 张发票，发票日期范围为 2009-01-01 至 2013-12-22。币种未注明。单价和金额在 SQLite 中的表示不用于真实财务结算。

| 能力 | 首版状态 | 后续产品方向 |
| --- | --- | --- |
| 问题输入与歧义澄清 | CLI 输入；模型可返回具体追问 | Web 表单和澄清控件 |

## 验收目标

离线验收要求：八个案例按预期得到成功或澄清状态；固定问题的结果与直接查询一致；故意错误的 `Amount` 字段能够改成 `Total`；攻击测试后数据库内容不变；超出预算能够停止。

真实模型验收使用至少 20 个独立问题，包含单表、多表、时间过滤、空结果和歧义问题。目标为结果正确率不低于 85%，危险访问拦截率 100%。正确率以审核过的结果和业务口径判定，不能只比较 SQL 字符串或是否成功执行。这是后续验收目标，尚未测量。

记录真实模型每题调用次数、耗时和失败阶段后，再据实际服务和模型设定延迟、费用目标，不把本地离线执行时间当作模型响应时间。

## 实施与风险

首版顺序为数据库解析、受控执行、模型阶段编排、错误恢复、案例与测试、文档和在线验收。当前已交付代码、离线验证和三份设计文档，在线验收需要配置模型。

主要风险是 SQL 能执行但口径错误、历史数据被误当实时数据、模型总结添加不存在的因果解释。应通过口径提示、审核过的基准问题、显示数据范围和原始结果控制这些风险。生产扩展前还需把用户权限与模型选表分离，采用数据库账号权限、隔离执行环境和受控日志。
