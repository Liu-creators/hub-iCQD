# 1、 langchain 工具调用 和1lm function call 有什么区别？

```
1. LLM Function Call（底层）

这是模型提供商（OpenAI、Anthropic、Google 等）在 API 层面提供的原生能力。
本质： 模型输出一个结构化的 JSON 对象，描述应该调用哪个函数以及传入什么参数，而不是直接输出文本。

2. LangChain 工具调用（上层封装）

LangChain 在 LLM function call 之上封装了一层，统一了不同厂商的差异。
内置执行循环调用工具并返回结果（Agent 模式）
内置错误重试、格式校验机制

```

# 2. langchain 工具调用的速度是受到什么影响？

```
1. 框架层开销（最显著）

原生 API 调用:  [用户请求] → LLM → [函数参数 JSON]
LangChain:     [用户请求] → LLM Schema 转换 → LLM → 输出解析 →
               函数执行 → 结果格式化 → LLM（第二轮）→ 最终回答

- Schema 序列化/反序列化：LangChain 每次调用都需要将 Python 函数签名转换为 LLM 能理解的 JSON Schema，再把 LLM 返回的 JSON 解析成 Python 对象。这个过程本身就有几十到几百毫秒的 CPU 开销。
- BaseModel 校验：Pydantic 模型校验（特别是复杂嵌套结构）会消耗额外时间。

2. Agent 循环次数（最大瓶颈）

# 原生 function call：1 次 LLM 调用 + 1 次函数执行
user → LLM → function → response  # 1 round trip

# LangChain Agent：可能有 N 次 LLM 调用
user → LLM → tool1 → LLM → tool2 → LLM → response  # N round trips

每个工具调用都走一次完整的 LLM 请求（包括网络传输、模型推理），这才是最耗时的——一次 LLM 调用通常 1-5 秒，Agent 多轮就是倍数级增长。

3. Prompt/Context 膨胀

# 每次工具调用后，会把结果追加到 messages 里
messages = [
    user_message,  # 原始问题
    system_prompt,  # 越来越长（工具描述）
    llm_response_1,  # tool call
    tool_result_1,   # 执行结果（可能很长）
    llm_response_2,  # 又一个 tool call
    tool_result_2,   # 又一个结果
    ...
]

- 每轮循环都会把完整对话历史传回 LLM
- 工具描述越多，system prompt 越长
- 工具返回的数据量越大，后续请求越长
- 上下文越长 → Token 处理越多 → 每轮 LLM 调用越慢

4. 工具选择与路由开销

当注册了多个工具时：
- 所有工具 Schema 都塞进每次 LLM 请求
- 模型需要从大量工具中"挑选"合适的那个
- 工具越多、Schema 越复杂，模型推理时间越长（注意力机制要扫描所有工具定义）
```
